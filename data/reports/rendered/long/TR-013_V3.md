# QR-Code Phishing Campaign Against Facilities Staff Using the "Marrowbill" Kit

## ACTIONS TO TAKE TODAY
1. Search proxy and DNS logs for the network indicators in Table 1.
2. Remove printed flyers with QR codes for "badge renewal" from shared areas.
3. Reset passwords of staff who scanned the code and entered credentials.

## SUMMARY
An actor tracked here as DUN SANDERLING (fictional) has placed printed flyers in office buildings
asking staff to renew their access badge by scanning a QR code. The code leads to a phishing kit
called Marrowbill that asks for the staff member's work password and a one-time code. Facilities
and real-estate companies are the main targets. Stolen credentials have been used for remote
log-ins within hours. No malware is installed, so network logs are the main evidence.

This activity matters beyond the organisations already affected. Organisations in the facilities management sector often share suppliers, managed service providers, and e-mail infrastructure, so a compromise at one organisation can expose its partners through trusted relationships. The board assesses with moderate confidence that further organisations in the facilities management sector have received similar messages but have not yet noticed them. Readers should treat the indicators in this report as a starting point for reviewing their own environment, not as a complete list.

The board will update this report if new information changes the assessment. Organisations that find matches are encouraged to share anonymised observations, such as the time ranges and the log sources involved, because these details help others judge whether their own findings are related.

## TECHNICAL DETAILS
### Initial Access
The QR code opens facility-badge-renew[.]example[.]org on the staff member's phone or, when the
link is typed in later, on a workstation [T1566.002]. The page imitates the company sign-in page.
### Credential Access
Entered passwords and one-time codes are forwarded in real time through the relay
mb-relay-07[.]example[.]net [T1557], so the actor can complete the sign-in before the code expires.
### Remote Access
Both actor domains resolve to 203.0.113.169. The actor signs in remotely from the same address
with the stolen credentials [T1078].

## DETECTION / HUNT RECOMMENDATIONS
- Search proxy logs for visits to both domains in Table 1 and connections to the IP address.
- Search DNS logs for lookups of both domains in Table 1.
- Phones on the guest network may not appear in workstation logs; ask staff directly.

### Additional guidance for investigators
- Write down the question the investigation must answer before starting, and stop when the evidence answers it. Open-ended investigations tend to grow without producing clearer results.
- Note the time zone of every log source. Comparing timestamps from sources that use different time zones is a common cause of false conclusions.
- Keep a short evidence table: host, log source, time, and why the row is relevant. A table like this makes hand-over between analysts much faster.
- Distinguish between hosts that only resolved a domain and hosts that also connected to it; the second group is usually the priority for containment.
- Do not alter or delete log data during an investigation. If data must be exported, keep the original copy unchanged.
- When the investigation ends, record what slowed it down, such as missing fields or short retention, so that the gaps can be fixed before the next incident.
- Ask a second analyst to review the list of affected hosts before it is reported. A short peer review catches copying mistakes and hosts that were included without enough evidence.
- Report the confidence of each finding in plain words, such as confirmed, likely, or possible, so that decision makers understand which conclusions are firm.
### Keeping an evidence record
A useful evidence record has one line per finding with the same fields every time: the host name, the log source, the time of the event, the indicator or behaviour that matched, and a short note on why the line matters. Analysts should add the time they made each entry and their initials. A record kept in this form can be handed to another team, attached to a ticket, or used later to build a timeline without having to search the logs again.

## MITIGATIONS
- Identity: move to phishing-resistant MFA that cannot be relayed.
- Physical: remove unapproved notices and tell staff how badge renewal really works.
- Monitoring: alert on remote log-ins from new addresses soon after a password change.

### Additional mitigations
**Prevention**
- Block macros and scripts in documents that arrive from the internet, and open such documents in a protected view by default.
- Remove local administrator rights from everyday user accounts.
- Keep a current inventory of hardware and software so that unmanaged devices are noticed.
- Apply security updates within a defined time limit, with a shorter limit for internet-facing systems.
**Detection**
- Collect proxy, DNS, and endpoint telemetry centrally, and check every week that each source is still sending data.
- Alert on new scheduled tasks or services created by non-administrative users.
- Review alert rules after each incident and remove rules that only produce noise.
**People and process**
- Train staff to recognise invoice- and delivery-themed lures, using short, regular exercises rather than one long annual course.
- Give the security team clear authority to isolate a device without waiting for a change window.
- Agree in advance how and when partners, customers, and regulators will be informed of an incident.
**Third parties**
- Ask key suppliers and service providers how they would notify you of a compromise on their side, and test that path once a year.
- Limit the access that suppliers have to your environment, and remove it when a contract ends.
**Recovery**
- Keep at least one copy of critical backups offline and test that it can be restored.
- Document the order in which business services must be restored, and check it with service owners every year.
- Prepare clean replacement devices for key staff so that work can continue while affected devices are rebuilt.
- After recovery, compare the incident timeline with the existing alerts to find the earliest point at which the activity could have been detected, and add or tune alerts for that point.
- Record the total time from first activity to detection and from detection to recovery, and track these numbers across incidents.
**Where to start**
Teams with limited time should apply these steps first, in this order:
1. Confirm that proxy, DNS, and endpoint logs are collected and can be searched for the full period covered by this report.
2. Turn on phishing-resistant multi-factor authentication for remote access and administrator accounts.
3. Block execution of unapproved programs from user-writable folders.
4. Make sure offline backups exist for the systems the business cannot run without.
5. Write down who may isolate a device and how to reach that person outside office hours.

## VALIDATE SECURITY CONTROLS
Applying the mitigations is only part of the work. Organisations should also check that their defences behave as expected against activity like the one described here. A simple cycle works for most teams:
1. Pick one behaviour from the Technical Details section.
2. Write down which control should stop it and which alert should fire if it is not stopped.
3. In a test environment you are authorised to use, run an approved, harmless simulation of the behaviour.
4. Note whether the control blocked it, whether the alert fired, and how long it took someone to notice.
5. Fix gaps in configuration, alert rules, or procedures, then repeat the same check.
Repeat the cycle for each behaviour in this report and keep the results, so that the next review can show whether coverage improved.

Useful measures for these checks include the share of behaviours that were blocked, the share that raised an alert, and the median time between the behaviour and the first human response. Tracking the same measures over several cycles shows whether investments in tools and training are working.
