# Typosquatted Developer Package Pulling the "Hollowpine" Stealer

## ACTIONS TO TAKE TODAY
1. Search proxy and DNS logs for the network indicators in Table 1.
2. Remove the package `colorlogx` from all developer machines and build caches.
3. Rotate access tokens stored on developer workstations that installed it.

## SUMMARY
An actor tracked here as VELVET SKUA (fictional) published a package named `colorlogx`, one letter
away from a popular logging library, on a fake package index. Developers who mistyped the name or
whose tools were pointed at the fake index installed it. A post-install step downloads a stealer
called Hollowpine that collects source-control and cloud access tokens. Several software companies
are affected. Any host that contacted the fake index or the drop server should have its tokens
rotated.

This activity matters beyond the organisations already affected. Organisations in the software sector often share suppliers, managed service providers, and e-mail infrastructure, so a compromise at one organisation can expose its partners through trusted relationships. The board assesses with moderate confidence that further organisations in the software sector have received similar messages but have not yet noticed them. Readers should treat the indicators in this report as a starting point for reviewing their own environment, not as a complete list.

The board will update this report if new information changes the assessment. Organisations that find matches are encouraged to share anonymised observations, such as the time ranges and the log sources involved, because these details help others judge whether their own findings are related.

## TECHNICAL DETAILS
### Initial Access
The package is served from pkg-index-fast[.]example[.]org, a look-alike package index
[T1195.001]. A shared setup guide circulated on a developer forum pointed tools at this index.
### Execution
On install, the package runs `devtools_postinstall.exe` [T1059], which fetches Hollowpine.
### Collection and Exfiltration
Hollowpine searches configuration files for access tokens [T1552.001] and sends them to
hp-drop[.]example[.]net, which resolves to 203.0.113.157 [T1041].

### Additional guidance for investigators
- Confirm that each match falls inside the activity window described in this report. Matches far outside that window are more likely to be coincidental.
- For every affected host, record the first and last time the activity was observed and which log source showed it. People who work on the same incident later will rely on this record.
- Treat a single match in one log source as a lead, not as a confirmed compromise. Matches that appear in more than one source give stronger evidence.
- Keep proxy, DNS, and endpoint detection data for at least 90 days so that later investigations can cover the full period of an activity.
- Share confirmed findings with the incident-response lead before any containment step, so that containment does not alert the actor early or destroy evidence.
- After the investigation, review which detections fired and which did not, and adjust alert thresholds so that similar activity is caught earlier next time.
- If a match cannot be explained, keep it in the evidence record with a note rather than discarding it; unexplained matches are often understood later, once more context is available.
- Agree on one shared place where all analysts store notes for the incident, so that findings are not spread across personal files and chat messages.
### Keeping an evidence record
A useful evidence record has one line per finding with the same fields every time: the host name, the log source, the time of the event, the indicator or behaviour that matched, and a short note on why the line matters. Analysts should add the time they made each entry and their initials. A record kept in this form can be handed to another team, attached to a ticket, or used later to build a timeline without having to search the logs again.

## MITIGATIONS
- Development: pin the approved package index in tool configuration; review new dependencies.
- Secrets: keep tokens in a secrets manager, not in configuration files.
- Monitoring: alert on post-install steps that start executables.

### Additional mitigations
**E-mail and web**
- Filter inbound e-mail for attachment types and links that are commonly used to deliver malware, and quarantine messages that fail sender-authentication checks.
- Show a clear banner on messages from outside the organisation, and give staff a one-click way to report suspicious messages to the security team.
- Use web filtering to block newly registered and uncategorised domains for most users.
**Endpoints**
- Keep operating systems, browsers, and office software up to date, and fix vulnerabilities that are known to be exploited first.
- Allow only approved applications to run from user-writable folders.
- Make sure endpoint detection agents are installed and healthy on every workstation and server, and raise an alert when an agent stops reporting.
**Identity and access**
- Require phishing-resistant multi-factor authentication for remote access and for administrative accounts.
- Give users and service accounts only the access they need, and review privileged group membership on a regular schedule.
- Disable accounts promptly when staff leave or change roles.
**Network**
- Segment networks so that a compromised workstation cannot reach servers it has no business need to reach.
- Restrict outbound traffic from servers to the destinations they actually require.
**Resilience**
- Keep offline, encrypted backups of critical data and test restoring them at least twice a year.
- Maintain and rehearse an incident-response plan that names who decides on containment, communication, and recovery.
**Logging**
- Make sure proxy, DNS, and endpoint logs record the host name, user, and an accurate timestamp for every event, and synchronise clocks across all systems.
- Protect log data from modification, and limit who can delete it.
- Test once a quarter that the security team can search the last 90 days of logs within minutes.
**Recovery after an incident**
- Rebuild compromised workstations from a known-good image instead of trying to clean them.
- Reset credentials that were used on affected hosts, starting with privileged accounts.
- Monitor previously affected hosts closely for several weeks after recovery, because actors often try to return through the same route.
- Hold a short review after recovery and assign an owner and a date to every improvement that is agreed.
**Where to start**
Teams with limited time should apply these steps first, in this order:
1. Confirm that proxy, DNS, and endpoint logs are collected and can be searched for the full period covered by this report.
2. Turn on phishing-resistant multi-factor authentication for remote access and administrator accounts.
3. Block execution of unapproved programs from user-writable folders.
4. Make sure offline backups exist for the systems the business cannot run without.
5. Write down who may isolate a device and how to reach that person outside office hours.

## VALIDATE SECURITY CONTROLS
Applying the mitigations is only part of the work. Organisations should also check that their defences behave as expected against activity like the one described here. A simple cycle works for most teams:
1. Pick one behaviour from the Technical Details section.
2. Write down which control should stop it and which alert should fire if it is not stopped.
3. In a test environment you are authorised to use, run an approved, harmless simulation of the behaviour.
4. Note whether the control blocked it, whether the alert fired, and how long it took someone to notice.
5. Fix gaps in configuration, alert rules, or procedures, then repeat the same check.
Repeat the cycle for each behaviour in this report and keep the results, so that the next review can show whether coverage improved.

Useful measures for these checks include the share of behaviours that were blocked, the share that raised an alert, and the median time between the behaviour and the first human response. Tracking the same measures over several cycles shows whether investments in tools and training are working.
